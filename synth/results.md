# CORDIC Synthesis Results

Target device: Xilinx Artix-7 `xc7a35tcpg236-1` (Basys3), Vivado 2024.2.
Clock constraint (both designs): `create_clock -period 10.00 -name clk [get_ports clk]` (100 MHz).
Design state: post-synthesis (`synth_1`), no place & route.

Both designs use the pipelined shift-add constant-multiply fix (partial sums
registered, then a registered mode-correction mux) rather than the original
single-cycle combinational tail, which is what closes timing here.

The iterative design's `finish` signal (iteration-count-complete, used
internally to gate the counter and freeze `cordic_iterative`'s registers) is
now purely internal, not a module output — it fires 2 cycles before the
output registers actually settle, so it was a footgun for any external
consumer. `done` (registered to align exactly with the final `x`/`y`/`z`
update) is the only output-ready signal exposed at the top level now.

`cordic_top` (both versions) is now genuinely parameterized: `#(parameter
WIDTH=16, parameter N=14)`, threaded through the full module hierarchy
(`cordic_stage`, `cordic_iterative`, `range_reduce`, `atan_mem`/`atan_val`).
`N` can be reduced below 14 freely (fewer iterations, lower precision,
functionally verified with `N=8`); increasing it requires extending the
arctan table past its current 14 precomputed entries. `WIDTH` is structurally
threaded through every port and internal signal, but the precomputed
Q3.13/Q2.14 constants (arctan table, HALF_PI, PI, the K-gain shift-add
decomposition) are numerically pinned to the default `WIDTH=16` format and
would need regenerating (e.g. via the Python golden model) for other widths.
All numbers in this report are for the shipped default `WIDTH=16, N=14`
configuration — re-verified bit-identical (WNS, LUT/FF/IOB counts) after the
parameterization refactor.

## Timing

| | Iterative (`rtl/cordic_top.v`) | Pipelined (`pipelined/cordic_top.v`) |
|---|---|---|
| Requested period | 10.00 ns (100 MHz) | 10.00 ns (100 MHz) |
| WNS (setup slack) | **+2.069 ns** | **+3.323 ns** |
| WHS (hold slack) | +0.153 ns | +0.158 ns |
| WPWS (pulse width slack) | +4.500 ns | +4.020 ns |
| Timing constraints met | Yes | Yes |
| Achievable Fmax (period − WNS) | **~126.1 MHz** | **~149.8 MHz** |

Both designs meet timing at 100 MHz with margin; the pipelined design has a
shallower critical path per stage (one `cordic_stage` hop vs. the iterative
version's shared, counter-driven stage plus its own combinational tail), so
its achievable Fmax is meaningfully higher despite using more resources.

## Resource Utilization (post-synthesis)

| Resource | Iterative | Pipelined | Available (device) |
|---|---|---|---|
| Slice LUTs | 491 (2.36%) | 1040 (5.00%) | 20,800 |
| Slice Registers (FFs) | 292 (0.70%) | 875 (2.10%) | 41,600 |
| DSP48 | 0 (0.00%) | 0 (0.00%) | 90 |
| Block RAM | 0 | 0 | 50 tiles |
| Bonded IOB | 100 (94.34%) | 99 (93.40%) | 106 |
| BUFGCTRL (clock buffer) | 1 | 1 | 32 |

Zero DSP usage on both — the CORDIC gain correction is applied via a
compile-time shift-add sequence rather than a hardware multiplier, and the
core rotation algorithm itself is add/shift only by construction.

The pipelined design uses roughly 2x the LUTs and 3x the registers of the
iterative version, since it instantiates 14 physical copies of the rotation
stage (`cordic_iterative`/`cordic_stage`) rather than reusing one stage over
14 cycles — the expected area/throughput trade-off. I/O pin count is nearly
identical and is the tighter constraint on this small device either way
(>90% of available IOBs used by both), driven by the six parallel 16-bit
x/y/z in/out ports rather than by logic complexity.

## Latency (post-synthesis, functional/simulation-verified)

| | Iterative | Pipelined |
|---|---|---|
| Cycles per result | 17 (1 load + 14 iterations + 2 output-register stages) | 17 (1 load + N=14 pipeline stages + 2 output-register stages), fixed and known at compile time |
| Throughput | 1 result per 17 cycles | 1 new result per cycle in steady state, once the pipeline is full (first result still takes 17 cycles to emerge) |

## Report files

Generated by `synth/extract_reports.tcl` against each project's `synth_1`
run (`open_project` + `open_run synth_1`, so XDC constraints are loaded):

- `synth/reports/iterative_utilization.rpt`
- `synth/reports/iterative_timing_summary.rpt`
- `synth/reports/iterative_worst_paths.rpt` (top 10 worst setup paths)
- `synth/reports/pipelined_utilization.rpt`
- `synth/reports/pipelined_timing_summary.rpt`
- `synth/reports/pipelined_worst_paths.rpt` (top 10 worst setup paths)

Source projects: `synth/cordic/cordic.xpr` (iterative),
`synth/cordic__pipeline/cordic__pipeline.xpr` (pipelined). Both reference
the live RTL under `rtl/` and `pipelined/` directly (sources were not
copied into the project), so re-running synthesis in Vivado picks up any
RTL edits automatically.
